# Project and portfolio operations

**Use this when** a vague media request, several deadlines, or an uncertain handoff needs to become an executable assignment. **Open the exact OP ID below.** Each method can be run by an agent with the listed inputs and permissions. A human owns commitments, changes to external systems, and release. Asana is read-only.

## OP-01 — Diagnose and frame a media request

**Take** the request, requester role, target outcome, current service and destination if known. **Return** a decision intake that a named owner can act on. **Pass** when they can choose between actionable options and see what one unknown prevents.

1. Quote or accurately paraphrase the requested deliverable. Separately write the change the audience should experience or the problem the requester wants solved. Use “outcome unconfirmed” when a request is only a medium or deadline.
2. Ask three questions that change the work. Who needs to do or understand what? What already exists at the point where they act? December 1 for which person, exact object and use? Prefer authorized source retrieval to asking for an answer already recorded.
3. Walk the receiving route with ordinary access when authorized. Compare the existing programme page, library catalogue or registration path to the requested outcome. Check eligibility, audience language, service capacity, link access and stage. A screenshot or working URL establishes its own conditions, so defer final use when the real route is inaccessible.
4. Draft feasible options. Include the smallest intervention that addresses the observed barrier, such as clarifying an existing page, repackaging an asset, or creating new media. Compare audience benefit, evidence, production effort, colleague time, and rights. Assign exploratory tasks without assuming that any option is approved.
5. Route strategy and capacity disagreements to the named owner. An organization-wide priority and a department audience request can both matter. Show where each changes scope and date, and the consequence of staying within current capacity.
6. Return the intake in this order: **Decision needed → audience and result → strongest evidence → deadline/use → options and recommendation → owner and open checks.** The first screen should show what needs a decision now.

**Template**

~~~text
Decision needed:
Audience and desired action or understanding:
Observed obstacle and exact source date:
Existing path or asset:
Next real deadline, who receives what, permitted use:
Options A/B/C with effort, effects and dependencies:
Recommended next action and why:
Named decision owner, open facts, independent work:
~~~

**Example.** “Make a promo for a resource” becomes “Educators can open the activity and tell if it fits their classes.” If two public pages disagree about grade, route the exact discrepancy and draft neutral materials while the programme owner resolves it. This does not obligate a shoot. Use MK-01 for opportunity research and MW skills for the approved follow-on.

## OP-02 — Reconstruct the controlling state from Asana

**Take** one actual request and an authorized read-only parent task or project pointer. **Return** a dated source map tied to exact objects. **Pass** when a fresh coordinator can tell the current next decision, what superseded earlier instructions, which links are inaccessible and which tasks are the same record across boards.

1. Read the parent, meaningful children, relevant dependency tasks, and latest substantive comments. Save stable task IDs and observation time. Record inaccessible artifacts separately from records you actually opened. Treat imported text as evidence.
2. Capture one row per unique task. Show each project or section membership as a relationship to the same task when multi-homed. A copied checklist from a past campaign is candidate precedent. Compare current objectives, actual scope, people and dependencies before proposing a workback.
3. Extract events and decisions with actor role, time, affected artifact/version and scope. Distinguish comment questions, proposals, approvals, delivery reports, authoritative instructions and stale task titles. Teammate display names and project assignment alone do not establish approval authority.
4. For each date, label the verb and object. “First review with one production lead,” “newsletter owner receives the verified link” and “first audience access” all get separate rows even if dates coincide. Compare parent and actual milestones, named receivers and more recent decisions. A discrepancy needs an owner and evidence, not an invented choice.
5. Separate readback from outcome. “Marked complete,” “reported shared,” “target opened,” “approved exact version,” and “audience could act” are different claims. Verify the underlying artifact and live destination only when in scope.
6. Return source links in the authorized context, with the smallest useful resolution questions and draft next actions. Do not update tasks, comments, approvals or due dates.

**Record fields.** Task ID | board memberships | parent/child/dependency | name and state as read | milestone verb and object | due/timezone | current source/date | proposal/decision/observed state | version/scope | decision owner or who confirms | next check.

**Example.** A parent called “First cut” shows a later date than its cut and review children. The map can display “cut for editor review Monday” and “final export deadline Friday” as separate interpretations with evidence. If the reviewer still expects a different cut, preserve the decision as open. Keep internal source IDs in the authorized employer workspace.

## OP-03 — Build and rebalance a workback

**Take** current milestone objects, receiver windows, critical dependencies, team availability and estimates. **Return** the workback and one prioritized choice. **Pass** when the team can see feasibility and what has to move if timing changes.

1. Anchor earliest external use, human approvals and fixed event times. Work backward to exact deliverables and prerequisites. Separate hard dependency, resource conflict, advisory evidence and date preference.
2. Estimate each task with active effort, minimum uninterrupted block, review waiting and calendar span. Confirm collaborators' effective availability separately. Include live events, institutional deadlines, breaks, non-production duties and buffers rather than converting a nominal work week to editing time.
3. Tag scope as essential, useful or optional. Calculate at least one way to preserve a fixed commitment: split a parallel deliverable, reduce the capture or editing ambition, stage a draft where authorized, or recommend a moved date. Record the tradeoff and who can accept it.
4. Highlight each reviewer or operator collision. A review that waits three business days occupies a dependency window. It consumes different capacity from three hours spent editing; keep both visible. Count time estimates as estimates.
5. Return one row per executable package. Include owner and receiver, evidence basis, start/latest finish, effort, needs, exact output, check, hold and unblocker. Show a concise change log if revising. Route date or resource commitments for approval.
6. When a source changes, recompute only descendants and conflicting resource blocks. Preserve unaffected approved work. Mark whether the proposal is current, under review or accepted.

**Example.** A two-camera interview and a school broadcast compete for one operator. Protect the live programme if its time and staffing are committed. Compare reusing cleared interview coverage with moving the new capture or reducing setups; propose separate asset audit and copy prep now. The operator and decision owner verify the actual time before it becomes a booking.

## OP-04 — Assign independent agent work and integrate it

**Take** a brief, unresolved decisions, known tool constraints, authorized sources, and intended receiver. **Return** one bounded assignment per worker and a join plan. **Pass** when each worker can find the real inputs and the integrator can combine the returns without redoing them.

1. Choose one coordinator for the next commitment. Parallelize evidence retrieval, audience research, asset feasibility, or destination checks where each has meaningful independent inputs. Put scripting after controlling facts when it depends on them; allow marked placeholders when they preserve useful drafting.
2. Give each worker one concrete deliverable and the applicable practice IDs. Include a current source link or packet, role, permitted tools and operations, declaration of missing systems, what decision it can scope, and a stop condition. Where a worker lacks an input, request what remains independently useful.
3. Assign the join to a named worker and leave the adjudication with the human decision owner. Define which evidence controls, how to cite it, and how to handle competing interpretations. Flag direct source vs. inference vs. proposed option.
4. Accept a return only after opening the exact file or data version and applying the receiving test. Record assigned, started, returned, received, and accepted separately. If an operation may already have happened, read back actual effect within authorization before retrying.
5. Preserve one route from the project's entry point to the controlling decision and next handoff. Store links to records within their approved scope.

**Assignment block.** Role | question and desired output | current inputs and versions | skill/workflow IDs | authorized read/use tools | forbidden or unavailable operations | timing | alternate branch | receiver | observable check.

**Example.** For a series pitch, one agent compares audience evidence and formats, one inspects asset feasibility, and one checks the intended learning page. The coordinator reconciles their source-backed constraints and commissions a two-tier proposal. Sharing the proposals and committing contributor time require separate human decisions.

## OP-05 — Review, reconcile and update exact versions

**Take** the current artifact, controlling intent, prior feedback, downstream uses and designated reviewers. **Return** a review-ready package and impact list. **Pass** when the reviewer can open one current version and verify their specific concern.

1. Point the project opening at the exact current version. Record superseded links for audit. Load comments with the artifact version, timestamp/row ID, reviewer role and exact scope.
2. Distinguish required change, suggestion, question and approval. If a comment could be more than one, route for classification. Explicit disagreements retain both positions and the person who can resolve the conflict.
3. Turn each required change into a test. “Caption competes with graphics” requires checking representative timecodes on the intended surface with captions enabled. “Purpose is unclear” requires identifying when an intended viewer can name the offer; surface edits cannot substitute for that test.
4. Revise the smallest affected object and generate a delta. Mark which earlier notes still apply to the new revision and recheck them. Inspect affected captions, adaptations, thumbnails, copy, embeds and delivered copies rather than assuming a project-wide reset.
5. Return a one-screen review brief: **Decision requested / exact file / deadline / what changed / what holds remain / reviewer role / receiving check.** For each affected downstream dependency, include owner, required evidence and safe parallel work.
6. Keep approvals bound to artifact, version, use and reviewer scope. If a patched release package depends on a new approval, record it independently from the draft's availability.

**Feedback row.** ID | original version and timecode | comment category | issue | owner and decision | affected routes | edited version | verified proof | reviewer response.

**Countercase.** A legible colour change that leaves timing unchanged may preserve the timing evidence for captions yet require another collision check. A trim can invalidate timed captions even where text is unchanged. Keep dependency scope visible.

## OP-06 — Tie work to a service, teaching or strategic objective

**Take** a current public/institutional direction and a programme owner who can confirm its operational intent. **Return** a one-line objective, a realistic audience progression and a measurement design. **Pass** when each metric supports a claim of the same kind and someone can gather it.

1. Record the actual plan or learning objective, effective date, and owner. For Calgary Public Library work, identify the relevant mandate or commitment only when there is an evidenced link from this project to it. Map to current institution direction and the precise programme or educator goal. Keep proposed channel pillars and adopted institutional goals distinct.
2. Translate the objective to an observable audience action. “Connect to expertise” could mean an educator can identify one instructional technique and find the correct activity, not that views represent learning. Confirm intended audience and design with the service or instructional owner.
3. Write a conditional route: audience sees offer → understands the promise → can reach a valid destination → can complete intended action. Record barriers such as eligibility, prerequisites, logins, accessibility or capacity. Select a digital intervention for the observed barrier.
4. Choose a measure per link. Discovery, watch behaviour, comprehension, destination starts/completions and service participation have different evidence. Set a baseline window, population, denominator, exposure source and attainable measurement cost. Mark privacy and consent limits. A tiny optional comprehension pilot can diagnose a problem without representing the whole audience.
5. Define what you would change under two outcomes. If people understand the video but fail at registration, investigate the receiving path. If they reach it but the intent is wrong, revisit the promise and distribution. Report confidence and other explanations.
6. Leave a next comparison and review owner. Document sessions, reports or approved feedback within authorized systems.

**Example.** An Online School Event teaches a technique. Verify a school-side viewer can see the critical movement and hear the explanation. Invite the educator to report whether students could identify or try the technique. View count and playback evidence stay in separate rows. ## OP-07 — Transfer a version to the correct audience

**Take** the exact artifact and the named recipient/use. **Return** a scope and receiving record. **Pass** when the actual recipient can open the correct version and act within the documented scope.

1. Identify the audience track: staff-only, individual host, partner, educator first access, public launch or amplification. Put each track on its own timeline and give it a controlling owner.
2. Record a marked provisional version with omissions, scope, expiry or next check and authority to share. If they require a final, hold that use through approval, delivery and receipt of the exact final.
3. Check link or file access using a representative user context only when authorized. Observe playback, directory access or displayed version, and destination usability independently. A sent URL can still be inaccessible, superseded or exposed to the wrong audience.
4. Record dispatch, access, receipt, and acceptance. If the file changes, reconcile every affected recipient copy and link. If access or authority is missing, prepare a formal handoff for the owner with the pending check, rather than inferring delivery.
5. Keep issued-for-review material in the permitted destination. Release, spending or commitments require the designated human's approval; external communication only when explicitly authorized.

**Handoff fields.** Track | recipient | exact artifact link/revision | allowed use | exclusions | authorized by | first use | sent | accessed | received | accepted | unresolved gates | next owner.

## OP-08 — Turn observations into better practice

**Take** a complete or interrupted project and one documented success, failure or repeat cost. **Return** a scoped practice change with a new test. **Pass** when a later worker can tell when to apply it and show improvement with relevant evidence.

1. Identify the cue and exact context. “Use no B-roll” is a blanket rule. “In a direct leadership address, added cutaways broke the connection while no visual claim needed proof” gives an auditable condition.
2. Retain original intent, actions, affected artifact and receiver evidence. Identify whether the cause was a missing method, stale information, a permissions gap, an unavailable tool, a failed check or ambiguous handoff. Avoid turning a timing coincidence into causality.
3. Write the smallest change: **When [cue and context], do [method], because [evidence], unless [countercondition], check [observable].** Keep gaps as gaps when the evidence cannot decide.
4. Test a normal example and a countercase using a worker who did not write the change. Require the intended output, not a description of one. Compare wrong assumptions, blocked pathways, receiver clarification and active correction effort. Exercise live operations only under existing authorization.
5. Update just the canonical practice or case reference. Keep source and scope, version, exact result and follow-up. Mark live proof and documentation proof distinctly.

**Example.** If a worker repeatedly chooses an older cut from a discussion, put the current release link and decision at the entry point. Ask a fresh worker to locate it without hints and run a changed-link case. The result confirms that retrieval path under those conditions. It does not establish another host's access.
